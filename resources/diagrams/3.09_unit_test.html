How a Unit Test Works
① you write BOTH sides, in staging.yml
unit_tests: - name: test_parse_salary_shapes model: stg_job_postings given: - input: source('jobs', 'raw_job_postings') rows: - {job_id: 1, job_salary: "100K–186K a year"} - {job_id: 2, job_salary: "32.50 an hour"} - {job_id: 3, job_salary: null} expect: rows: - {job_id: 1, salary_min: 100000, salary_max: 186000} - {job_id: 2, salary_min: 32.5, salary_max: 32.5} - {job_id: 3, salary_min: null, salary_max: null}
given: fake rows that stand in for the source.
three shapes you can check by hand
expect: the rows the model MUST produce from them.
only the columns you list are compared
② dbt runs the model on the fake rows, then compares
given rows
⚙️ stg_job_postings
parse_salary('min') · parse_salary('max')
runs before the build · reads none of your tables
what it produced
expect rows
=?
same → PASS
different → FAIL
The data changes every night. The logic should not.
