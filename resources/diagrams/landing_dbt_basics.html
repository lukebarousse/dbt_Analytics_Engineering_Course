MODEL
One SELECT in a .sql file. The file name becomes the object name.
-- models/job_postings.sql SELECT job_id, job_title, company_name FROM read_parquet('raw/*')
📄
job_postings.sql
dbt run
🗄️
job_postings (view)
- Lives in models/
- Built as a view by default
- dbt writes the CREATE
ref()
Point at another model. dbt builds the parent first.
-- models/jobs_per_month.sql SELECT DATE_TRUNC('month', search_date) AS month, COUNT(*) AS postings FROM {{ ref('job_postings') }} GROUP BY month
job_postings
jobs_per_month
- No hardcoded table names. The graph decides the build order
source()
Declare raw data once in YAML. Reference it everywhere.
# models/sources.yml sources: - name: raw tables: - name: job_postings
FROM {{ source('raw', 'job_postings') }}
raw.job_postings
job_postings
- One path to change. Sources show in the DAG
TESTS
Say what the data must be. dbt checks it on every build.
# models/schema.yml - name: monthly_summary columns: - name: month data_tests: - unique - not_null
$ dbt test PASS unique_month PASS not_null_month Done. PASS=2 ERROR=0 TOTAL=2
- Four built-in tests:
unique · not_null · accepted_values · relationships
- A failing test stops what depends on it
MATERIALIZATIONS
How dbt saves a model in the warehouse.
# dbt_project.yml models: analytics: +materialized: table staging: +materialized: view
🔍 view
query saved,
recomputed on read
🗄️ table
data saved,
fast reads
- Per folder in dbt_project.yml
- Or per model with config()
- Also: incremental and ephemeral
dbt build
Seed, run, and test in one pass, in DAG order.
$ dbt build 1 of 9 OK created view job_postings 2 of 9 PASS not_null_job_postings_job_title 3 of 9 OK created table jobs_per_month 4 of 9 OK created table monthly_summary ... Done. PASS=5 WARN=0 ERROR=0 TOTAL=9
- Tests run right after their model builds
- A failed test skips everything downstream
- Same command on your laptop and in CI
